## Summary of the feature
Add 5-8 player support. Rules are identical to 2-4P; the changes are the store pyramid
geometry, a doubled card pool (second physical deck), one special-card duplicate rule, and
UI that fits more players without degrading the 2-4P look.

## Confirmed design decisions

### Pyramid geometry
- Keep the existing 4P triangle as a fixed **cap**: rows 1,2,3,4,5,6,7 = 28 cards, widest row 7.
- Append **one flat row of 7 per player beyond 4**.
- Card counts per act: **5P=35, 6P=42, 7P=49, 8P=56** (= `28 + 7·(numPlayers-4)`).
- **Brick offset** (CONFIRMED): each flat row offset a half-card opposite the row above, so
  the block stays within a ~7.5-card-wide footprint (table-space win vs. staircase, which
  drifts ~2 cards diagonally by 8P). Interior keeps "2 cards cover 1"; row ends are covered
  by 1 (ragged edge — accepted, standard solitaire behavior).
- Bottom row starts face-up; `revealUncovered` continues to flip uncovered cards.

### Covering logic — REFACTOR to geometry-based (CONFIRMED approach)
- Current `isCardCovered` ([play.js:1390](../src/play.js)) uses fixed index math
  (`nextRow[col]` / `nextRow[col+1]`) which only works because the triangle always centers.
- Brick's offset alternates direction per row → fixed indices would need per-row special-casing.
- **Decision:** give each pyramid row an explicit **x-offset** (where col 0's center sits, in
  card units) and derive "covered?" from **horizontal overlap** with the row below. This
  handles triangle + brick + staircase uniformly and matches whatever is physically printed.

### Card pool — doubled (second deck)
- `STORE_CARDS` is **84 entries** (NOT 55 — that's the 2P total). Per-act 4P pool = exactly 28
  distinct (Act1 17+4+7, Act2 17+4+7, Act3 21+0+7). There is no `minPlayers: 5+` tier — the 4P
  pool already IS the full per-act pool.
- For 5-8P, `getActPool` ([play.js:1200](../src/play.js)) must return the act pool **doubled**
  (two copies of each of the 28). `buildPyramid` then slices the 35-56 it needs. 8P uses exactly
  two complete copies per act.
- Physical implication: 2× every store card + 8 starter decks (80 starter cards).
- **Duplicate-id audit needed** (uid stays unique via `createCardInstance`, but `card.id` now
  repeats in one pyramid): check `swap_revealed` (resolves pile targets by id) and any traj
  id→template mapping. Likely fine but verify.

### Buy-first duplicate rule (CONFIRMED)
Only `burn_buy_first` / **card_14** is self-contradicting under the doubled pool (two players
can't both be "buy/burn 1st"). Every other special either stacks cleanly or is per-player —
NO others need this treatment. Rule applies **only in 5-8P** (only place a 2nd card_14 exists).
- **Atomic claim:** per-round node under `games/{code}/` (e.g. `buyFirstClaim/{round}`), claimed
  via `runTransaction` — same pattern as `lobby.js` slot claim. First writer wins.
  `games/$gameCode` is already fully open → **no database.rules.json change** for this node.
- **Lost claim → activation no-ops:** in `activateSpecialCard` ([play.js ~3800](../src/play.js))
  and the AI path in `aiDrawPhase`. Card stays in hand, discards normally at round end via
  `resetPlayerRound` ([play.js:1491](../src/play.js)). No card-lifecycle special-casing.
- **AI + sim parity (CONFIRMED):** AI routes through the same atomic claim; `sim/ai-player.js`
  + `sim/evolve.js` get a round-scoped one-buy-first flag (no Firebase in sim).

### Trajectory capture — SKIP for 5-8P (CONFIRMED)
Trajectory ("daq") is a research side-channel with zero gameplay effect. Full support would
need writer + rules + the offline reconstructor (`sim/game-core.js`) to learn the new geometry,
and would pollute the ≤4P benchmark corpus. **Decision:** guard `trajLog*` to no-op when
`numPlayers > 4`. Revisit later if big-game data is wanted.
